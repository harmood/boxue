## 1. 项目概述

### 1.1 软件名称

**博学（Boxue）**

### 1.2 一句话定位

博学是一个面向个人学习者的多端学习平台。当前阶段以“题库 + 刷题 + 错题复习”为核心，后续逐步扩展为包含课程、学习计划、主观题、编程题等能力的综合性学习平台。

### 1.3 当前阶段目标

现阶段只完成刷题及其附属功能，包括：

- 题库创建与管理
- 题目创建与编辑
- 单选、多选、判断、填空四种题型
- 题目和选项支持图片
- 练习与作答记录
- 错题本、收藏、笔记
- 复习计划与学习统计
- Web、桌面端、Android 三端功能对等
- 多端数据同步
- 开放注册、用户管理、角色与权限管理
- 第一阶段支持 LaTeX 公式
- 预留 AI 扩展接口，但暂不实现 AI 功能
- 开发者/管理人员使用的管理后台与监控平台

### 1.4 长期目标

在刷题功能稳定后，逐步扩展为综合性学习平台：

- 主观题、编程题
- 课程、章节、课时
- 学习计划、闪卡、考试模拟
- 题库分享、班级/小组、教师/学生
- AI 解析、AI 出题、AI 学习助手
- 公开题库、内容审核、订阅与支付

## 2. 产品原则

### 2.1 三个用户客户端功能对等

Web、桌面端、Android 不是按“功能分工”设计的，而是面向不同使用场景：

- Web：无需安装，适合桌面浏览器、快速访问、跨设备使用
- 桌面端：适合长时间学习、本地文件导入、离线使用、系统级能力
- Android：适合碎片时间、移动场景、拍照采集、通知提醒

三端的**核心功能应保持一致**：

- 登录与账号
- 题库管理
- 题目创建与编辑
- 题目导入与导出
- 练习
- 错题本
- 收藏与笔记
- 学习统计
- 多端同步
- 设置与数据管理

平台差异只体现在交互方式和增强能力上，而不是“某个功能只有某一端才有”。

### 2.2 多端同步是核心能力

多端同步不是附属功能，而是博学的基础能力。

用户应该能够：

- 在 Web 上创建题库，在 Android 上继续刷题
- 在桌面端离线练习，联网后同步到 Web
- 在任意设备查看错题、笔记和统计
- 在任意设备继续上一次练习
- 在设备更换后恢复完整学习数据

因此，客户端采用本地数据库 + 服务端同步的架构，而不是纯在线表单应用。

### 2.3 后端分为“业务服务端”和“管理后台”

“后端”在项目中拆成两个概念：

1. **业务服务端（Server API）**
   - 为 Web、桌面端、Android 提供 API
   - 负责认证、同步、题库、练习、复习、媒体、导入任务
   - 普通用户通过客户端间接使用，不直接访问

2. **管理后台（Admin Console）**
   - 面向开发者和运营管理人员
   - 负责用户管理、内容管理、系统监控、日志、公告、功能开关
   - 普通用户不接触，也不在用户客户端中暴露入口

这样可以同时满足：

- 普通用户只需要使用客户端
- 开发者和管理人员有独立的管理与监控入口
- 业务 API 和管理后台可以共享同一套后端服务，也可以后续拆分部署

### 2.4 现阶段控制范围

当前阶段不做：

- 主观题和简答题
- 编程题和在线判题
- 视频课程
- 直播
- 社区、排行榜、评论
- 多机构、多租户
- 支付与订阅
- 公开题库市场
- AI 解析、AI 出题、AI 讲解等实际 AI 功能（只预留接口）

这些功能进入后续阶段，不在第一版中实现。  
第一阶段开放注册，因此必须同时实现用户管理、角色管理、权限控制和滥用防护。

## 3. 用户与角色

### 3.1 普通用户

普通用户是博学的核心用户，可以使用：

- 浏览和管理自己的题库
- 创建、编辑、导入、导出题目
- 进行练习和模拟考试
- 查看错题、收藏、笔记
- 查看学习统计和复习计划
- 在多个设备之间同步数据

普通用户既是“做题者”，也可以是“出题者”。当前阶段不强制区分“做题者”和“出题者”这两个业务身份，但账号层面必须区分普通用户和管理员。

第一阶段开放注册，默认注册角色为 `USER`。用户注册后可以：

- 创建自己的题库和题目
- 练习自己的题库
- 在 Web、桌面端、Android 之间同步数据
- 管理自己的设备、密码和个人资料

题库默认私有，用户之间的数据通过 `owner_id` 隔离。

### 3.2 开发者 / 管理员

管理员使用独立的管理后台，负责：

- 查看系统运行状态
- 监控 API、同步、数据库、存储、任务队列
- 用户管理：查询、启用/禁用、重置密码、强制下线、查看设备
- 角色管理：创建角色、分配权限、给用户分配角色
- 内容管理：题库和题目统计、异常内容处理
- 查看日志和审计记录
- 发布公告和功能开关
- 处理异常数据和用户反馈

管理员不通过普通用户客户端进入管理功能。

### 3.2.1 第一阶段的角色模型

第一阶段至少实现以下角色：

| 角色 | 说明 |
| --- | --- |
| `USER` | 普通注册用户，默认角色 |
| `ADMIN` | 管理员，可进入管理后台 |

权限采用 RBAC：

- 一个用户可以有多个角色
- 一个角色可以有多个权限
- 后端接口按权限校验，而不是只判断角色名称
- 管理员分配角色和修改权限时必须写审计日志
- 系统必须保护最后一个管理员，不能把所有管理员都删除或降级
- 初始管理员必须通过部署脚本、CLI 或环境变量创建，不能通过开放注册获得 `ADMIN`

第一阶段建议的权限：

```text
USER_BASIC
ADMIN_USER_READ
ADMIN_USER_WRITE
ADMIN_ROLE_READ
ADMIN_ROLE_WRITE
ADMIN_CONTENT_READ
ADMIN_MONITOR_READ
ADMIN_AUDIT_READ
ADMIN_SYSTEM_CONFIG
```

后续再增加内容审核、运营、客服等细分角色。

### 3.3 后续可能增加的角色

- 内容审核员
- 运营管理员
- 客服
- 题库作者
- 教师 / 学生
- 班级管理员
- 机构管理员

这些角色通过 RBAC 逐步增加，不需要修改用户表结构。

- 邮箱/用户名注册
- 邮箱验证（可配置是否强制）

- 修改密码
- 个人资料
- 设备列表

- 注销账号与数据删除
- 登录失败限流和账号锁定

角色与权限：

- 默认注册角色为 `USER`
- 管理员角色为 `ADMIN`
- 管理员可在管理后台分配角色

## 6. 题库建设

### 6.1 第一阶段：知识型题库

第一阶段只实现四种客观题：

1. 单选题
2. 多选题
3. 判断题
4. 填空题

暂不实现：

- 主观题
- 简答题
- 论述题
- 编程题

### 6.2 图片支持

图片不是独立题型，而是题目内容的一部分。

四种题型都支持：

- 题干图片
- 选项图片
- 解析图片
- 题目内多张图片

图片存储要求：

- 图片上传到对象存储或本地媒体目录
- 数据库只保存媒体元数据和引用
- 不使用 Base64 直接存数据库
- 支持 JPEG、PNG、WebP
- 第一阶段不建议允许 SVG，避免脚本注入风险
- 图片需要生成缩略图
- 支持图片压缩和大小限制
- 支持 alt 文本，方便无障碍阅读

跨端内容格式建议：

```text
题干/选项/解析：Markdown 子集
图片引用：media://<media_id>
公式：$...$ / $$...$$（第一阶段支持）
```

这样做的好处：

- Vue/Electron 可以用 Markdown 渲染
- Flutter 可以用 flutter_markdown 渲染
- 不依赖某一端的 HTML 渲染能力
- 第一阶段即可支持公式，后续可以扩展代码块

### 6.3 题型定义

#### 单选题

- 至少两个选项
- 只有一个正确答案
- 支持选项图片
- 默认全对得分

#### 多选题

- 至少两个选项
- 一个或多个正确答案
- 第一阶段默认全对才得分
- 后续可配置部分得分

#### 判断题

- 正确/错误两个选项
- 答案使用布尔值
- 支持题干图片和解析图片

#### 填空题

- 支持一个或多个空
- 每个空支持多个可接受答案
- 第一阶段使用标准化后的精确匹配
- 可配置是否忽略大小写
- 可配置是否忽略首尾空格
- 暂不支持正则表达式答案
- 暂不支持主观评分

### 6.3.1 公式支持

第一阶段公式直接作为题目内容的一部分，不是独立题型。

支持范围：

- 题干
- 选项
- 答案解析
- 判断题题干
- 填空题题干

第一阶段的填空答案仍按文本匹配，不对公式答案做自动判等。

格式约定：

```text
行内公式：$...$
块级公式：$$...$$
```

渲染方案：

- Web / Electron：KaTeX
- Android：flutter_math_fork 或同类 LaTeX 渲染库
- 复杂公式或不兼容语法：服务端渲染为 SVG 作为兜底
- 服务端保存原始 LaTeX，不保存渲染后的图片作为唯一内容

编辑方式：

- Web / Electron 提供 LaTeX 输入和实时预览
- Android 提供 LaTeX 输入、公式工具栏和预览
- 第一阶段不做可视化公式编辑器

安全要求：

- KaTeX 关闭 `trust`，限制危险命令
- 服务端对公式做白名单校验
- 渲染结果缓存，缓存键包含公式内容和渲染版本

跨端一致性：

- 建立“支持的 LaTeX 子集”清单
- 三端渲染快照测试
- 不支持的语法必须给出明确提示

### 6.4 题目状态

建议题目状态：

```text
DRAFT      草稿
PUBLISHED  已发布
ARCHIVED   已归档
```

当前阶段题库默认私有。后续公开题库需要增加审核状态：

```text
PENDING_REVIEW
APPROVED
REJECTED
```

### 6.5 题目去重

导入和创建时建议做基础去重：

- 标准化题干
- 标准化选项
- 计算内容哈希
- 同一题库内提示重复
- 允许用户选择“仍然导入”

### 6.6 第二阶段：主观题与编程题

第二阶段扩展：

- 主观题：富文本作答、评分标准、人工评分、AI 辅助评分
- 编程题：代码编辑器、测试用例、沙箱判题、多语言运行时
- 编程题需要独立的 Judge 服务
- 不允许在主 API 进程中直接执行用户代码

## 7. 多端同步设计

### 7.1 同步目标

同步范围：

- 题库
- 题目
- 题目版本
- 标签和知识点
- 图片等媒体元数据
- 练习会话
- 作答记录
- 错题
- 收藏
- 笔记
- 复习状态
- 用户设置

不通过客户端同步的数据：

- 用户账号、角色、权限
- 管理员操作
- 审计日志
- 系统配置
- AI 任务和用量

这些数据由服务端权威管理。客户端只缓存当前用户的资料、角色和权限摘要，并在登录或权限变更后刷新。

### 7.2 本地数据库

| 客户端 | 本地存储 |
| --- | --- |
| Web | IndexedDB（Dexie） |
| Electron | SQLite |
| Android | SQLite（Drift） |
| 服务端 | PostgreSQL |

### 7.3 同步模型

采用“本地优先 + 服务端序列号”的增量同步：

- 每个用户有独立的同步序列
- 服务端为每次变更分配递增的 `change_seq`
- 客户端保存自己的 `sync_cursor`
- 客户端拉取 `change_seq > sync_cursor` 的变更
- 客户端本地修改先写入本地数据库和待上传队列
- 联网后批量推送到服务端
- 服务端返回接受、拒绝和冲突结果

### 7.4 同步 API 草案

```text
GET  /api/v1/sync/pull?cursor={seq}&limit=500
POST /api/v1/sync/push
POST /api/v1/devices/register
GET  /api/v1/devices
DELETE /api/v1/devices/{deviceId}
```

拉取响应：

```json
{
  "changes": [],
  "nextCursor": 12345,
  "hasMore": false,
  "serverTime": "2026-11-19T10:00:00Z"
}
```

推送请求：

```json
{
  "deviceId": "device-uuid",
  "changes": [
    {
      "clientChangeId": "uuid",
      "entityType": "ATTEMPT",
      "entityId": "uuid",
      "operation": "CREATE",
      "baseVersion": 0,
      "payload": {}
    }
  ]
}
```

### 7.5 冲突处理策略

| 数据类型 | 策略 |
| --- | --- |
| 作答记录 Attempt | 追加写入，不冲突 |
| 练习会话 Session | 乐观锁；同一会话同一时间只允许一个活跃设备 |
| 笔记 Note | 最后写入优先，保留冲突副本 |
| 收藏 Favorite | 最后写入优先 |
| 用户设置 | 最后写入优先 |
| 题目/题库 Question/Bank | 乐观锁；版本冲突时要求合并或另存副本 |
| 复习状态 ReviewState | 服务端根据作答记录计算，客户端只缓存 |
| 删除 | 软删除 + 墓碑记录 |

原则：

- 不静默覆盖用户题目内容
- 作答历史不可丢
- 冲突必须可见、可恢复
- 服务端时间是同步权威时间

### 7.6 媒体同步

- 图片按内容哈希去重
- 上传成功后再引用
- 客户端按需下载
- 本地缓存可清理
- 离线时允许先引用本地临时文件，联网后补传

### 7.7 离线策略

- Electron 和 Android 支持完整离线题库
- Web 使用 IndexedDB 缓存题目和作答，支持有限离线
- 所有客户端维护待同步队列
- 网络恢复后自动重试
- 同步失败不影响本地继续使用
- 提供“立即同步”和“同步状态”界面

### 7.8 同步测试

必须覆盖：

- 两台设备离线修改同一道题
- 手机离线答题后联网
- 电脑和手机同时继续同一练习
- 重复上传同一条作答
- 删除后另一台设备修改
- 大题库首次同步
- 图片上传中断和重试
- 时钟不一致

### 9.3 选型说明

#### Vue 3

- 市场使用率高
- 生态成熟
- TypeScript 支持好
- 适合 Web 和管理后台
- 可以与 Electron 复用渲染层代码

#### Spring Boot

- Java 生态成熟
- 企业使用率高
- Spring Security、Spring Data、Spring Batch、Spring Actuator 等组件完整
- 适合认证、后台任务、监控和管理后台
- 后续扩展多用户、权限、审核和支付较自然

#### Electron

- 桌面端生态成熟
- 可以复用 Vue 3 前端代码
- 文件系统、SQLite、自动更新等能力完整
- 市场使用率高
- 代价是安装包和内存占用较大，需要接受

#### Flutter

- 一套代码支持 Android，后续可扩展 iOS
- UI 一致性好
- 社区和插件生态成熟
- 适合移动端离线、通知、相机等场景

#### PostgreSQL

- 事务和一致性能力强
- JSONB 适合题目载荷
- 索引、全文搜索、扩展丰富
- 市场使用率高
- 适合从个人项目扩展到多用户平台

#### 公式渲染

- Web / Electron 使用 KaTeX
- Android 使用 flutter_math_fork 或同类库
- 服务端保留 SVG 兜底渲染，解决跨端兼容问题
- 题目内容保存原始 LaTeX，渲染结果只作为缓存

#### AI 扩展

- 第一阶段不接入任何 AI 服务
- 后端预留 `AiTaskService`、`AiProvider` 等接口
- 预留任务表、用量表、功能开关和审计字段
- 所有 AI 能力默认关闭，后续按功能开关逐步启用
- AI 不能进入答题、判分和同步的关键路径

### 9.4 关键技术决策

- 后端：模块化单体，不拆微服务
- 客户端：三端功能对等，平台交互差异化
- 账号：开放注册 + RBAC 角色权限模型
- 同步：本地优先 + 增量同步 + 服务端序列号
- 内容：Markdown 子集 + 媒体引用 + LaTeX 公式
- 数据：PostgreSQL 为服务端权威数据源
- 管理：独立 Admin Console，不与用户客户端混合
- AI：只预留接口、任务表和功能开关，第一阶段不启用
- 判题：第二阶段独立 Judge 服务

## 13. 安全与隐私

### 13.1 账号安全

- 密码使用 Argon2id 或 BCrypt 哈希
- 开放注册接口按 IP/设备限流
- 登录失败限流和临时锁定
- 邮箱验证（可配置强制）
- Refresh Token 轮换
- 设备可撤销
- 管理员 2FA
- 管理员分配角色、禁用用户等敏感操作记录审计日志
- 防止最后一个管理员被删除或降级
- 注册和登录支持验证码/人机校验（可配置）

### 13.2 数据隔离

- 所有用户数据带 `owner_id`
- 服务端查询必须校验当前用户
- 管理后台访问需要 `ADMIN` 角色和对应权限
- 管理员查看用户数据必须经过审计
- 用户角色和权限由服务端权威管理，客户端不能自行提升权限
- 后续多租户增加 `tenant_id`

### 13.3 内容安全

- 富文本服务端过滤

## 18. 风险与对策

### 18.1 三端功能对等成本高

风险：三端都做完整功能，UI 和测试工作量会显著增加。

对策：

- 先做最小跨端闭环
- 共享 OpenAPI 契约
- Web 与 Electron 复用 Vue 代码
- 建立功能对等矩阵
- 平台差异只放在交互层

### 18.2 同步是最难的部分

风险：离线修改、多设备冲突、图片同步、练习会话恢复。

对策：

- 服务端序列号 + 增量同步
- 作答追加写入
- 题目乐观锁
- 冲突可见、可恢复
- 自动化多设备同步测试

### 18.3 Electron 体积和安全

风险：安装包大、内存占用高、桌面安全配置复杂。

对策：

- 接受 Electron 的体积代价
- 使用安全默认配置
- 禁用 Node 集成
- 使用 preload 最小暴露
- 代码签名和自动更新
- 不在渲染进程直接访问文件系统

### 18.4 Flutter 富文本编辑

风险：Flutter 端复杂富文本编辑体验不如 Web。

对策：

- 使用 Markdown 子集 + 图片引用
- Android 提供简化编辑器
- 复杂排版优先在 Web/桌面端完成
- 三端都能完成核心创建和编辑

### 18.5 中文全文搜索

风险：PostgreSQL 默认中文分词能力有限。

对策：

- 初期使用 `pg_jieba` 或 `zhparser`
- 或引入 Meilisearch/Elasticsearch
- 搜索与主数据库解耦

### 18.6 范围膨胀

风险：从刷题扩展到课程、社区、支付，导致第一版无法完成。

对策：

- 当前阶段只做刷题及附属功能
- 新需求进入后续路线图
- 每个阶段有明确验收标准

### 18.7 版权和内容合规

风险：导入的题库可能涉及版权。

对策：

- 题库默认私有
- 公开分享前增加审核
- 提供举报和下架机制
- 不默认分发用户导入的内容

### 18.8 开放注册带来的滥用风险

风险：公开注册接口可能被批量注册、撞库、刷接口或滥用存储。

对策：

- 注册和登录限流
- 邮箱验证
- 验证码/人机校验可配置
- 密码强度策略
- 账号锁定和异常登录检测
- 新用户存储配额
- 管理后台可禁用账号

### 18.9 三端公式渲染不一致

风险：KaTeX 与 Flutter 公式渲染库支持的语法不完全一致。

对策：

- 定义受支持的 LaTeX 子集
- 三端渲染快照测试
- 服务端 SVG 兜底
- 编辑时提示不支持的语法
- 不把渲染图片作为唯一内容

### 18.10 AI 预留接口导致范围膨胀

风险：为了“以后接 AI”提前引入过多抽象、任务系统和第三方依赖。

对策：

- 第一阶段只保留接口、任务表和功能开关
- 不接入任何 AI Provider
- AI 不进入答题、判分、同步关键路径
- 后续按具体场景逐步实现

### 18.11 角色权限设计错误

风险：角色和权限设计过粗或过细，可能导致越权或维护困难。

对策：

- 第一阶段只做 `USER` 和 `ADMIN`
- 使用权限码而不是在代码中散落角色判断
- 管理接口全部经过权限校验
- 关键权限变更写审计日志
- 保护最后一个管理员
- 增加越权测试

## 19. 关键决策记录

### ADR-001：三个用户客户端功能对等

决定：Web、桌面端、Android 核心功能保持一致，平台差异只体现在交互和增强能力。

原因：适配不同使用场景，而不是把功能拆散。

### ADR-002：后端拆分为业务服务端和管理后台

决定：业务 API 为客户端服务；管理后台为开发者和运营人员服务。

原因：普通用户不需要管理界面，管理和监控需要独立权限和安全边界。

### ADR-003：模块化单体

决定：第一版使用 Spring Boot 模块化单体，不拆微服务。

原因：降低部署和开发复杂度，保留后续拆分空间。

### ADR-004：本地优先 + 增量同步

决定：三端本地数据库 + 服务端增量同步。

原因：离线可用、多端体验一致，符合核心需求。

### ADR-005：Markdown 子集作为内容格式

决定：题干、选项、解析使用 Markdown 子集 + 媒体引用。

原因：Vue/Electron 和 Flutter 都能稳定渲染，避免 HTML 绑定。

### ADR-006：PostgreSQL + JSONB

决定：服务端主数据库使用 PostgreSQL，题型特有字段使用 JSONB。

原因：事务、查询、扩展和 JSON 支持兼顾。

### ADR-007：第二阶段独立 Judge 服务

决定：编程题判题不放在主 API 进程中。

原因：安全隔离、资源限制和独立扩展。

### ADR-008：Electron 复用 Vue 3

决定：桌面端使用 Electron + Vue 3，尽量复用 Web 的渲染层代码。

原因：提高开发效率，符合市场使用率和生态要求。

### ADR-009：Flutter Android 优先

决定：移动端先做 Android，后续可利用 Flutter 扩展 iOS。

原因：当前目标是 Android，同时保留跨平台空间。

### ADR-010：开放注册与 RBAC

决定：第一阶段开放注册，并实现用户、角色、权限管理。

原因：

- 产品目标是多用户学习平台
- 需要管理后台进行用户和权限管理
- 后续题库分享、班级、教师/学生都依赖账号和权限体系
- 采用 RBAC，避免把权限逻辑硬编码在业务代码中

### ADR-011：第一阶段支持 LaTeX 公式

决定：题干、选项、解析支持 LaTeX；Web/Electron 使用 KaTeX，Android 使用 flutter_math_fork，服务端保留 SVG 兜底。

原因：

- 数学、物理、化学等学习场景需要公式
- 跨端渲染需要统一格式和降级方案
- 保存原始 LaTeX 比保存渲染图片更可维护

### ADR-012：AI 只预留接口

决定：第一阶段不接入 AI，只预留 Provider 接口、任务表、用量表、审计字段和功能开关。

原因：

- 避免过早引入复杂依赖和成本
- 保留后续扩展空间
- AI 不应影响第一阶段的稳定性和核心链路
