# 刷题与学习平台：产品与技术分析

> 状态：早期分析稿，已被 `docs/project-charter.md` 取代。  
> 最新项目决策以 `project-charter.md` 为准。

## 1. 结论

这个方向适合作为个人项目，而且比“通用笔记/收藏工具”更容易形成完整闭环。

核心不是先做一个“大而全的学习平台”，而是先做一个真正好用的个人刷题系统：

```text
导入/创建题目
    -> 结构化题库
    -> 练习/考试
    -> 记录作答
    -> 错题与薄弱点
    -> 间隔复习
    -> 掌握度更新
    -> 再练习
```

这个闭环同时具备：

- Web：题库管理、练习、统计、导入审核
- 后端：同步、存储、搜索、复习调度、后台任务
- 桌面端：批量导入、OCR、本地题库、离线练习
- Android：每日复习、碎片时间刷题、拍照采集、通知提醒

四个平台都有自然职责，不是为了凑技术栈而存在。

但“学习软件”这个词很大，必须控制边界。第一版应定位为：

> 个人题库 + 错题驱动 + 间隔重复 + 多端同步的刷题工具。

而不是第一版就做课程、直播、社区、支付和内容商城。

## 2. 先确认一个关键分叉：考试题库还是编程题

“刷题”可能指两种完全不同的产品。

### A. 知识型题库

适合：考研、考公、语言考试、证书考试、专业课、通识知识等。

题型：

- 单选题
- 多选题
- 判断题
- 填空题
- 简答题
- 论述题
- 闪卡
- 带图片、公式、音频的题目

技术重点：

- 富文本和公式渲染
- 题目导入与清洗
- 错题本
- 间隔重复
- 知识点统计
- 移动端离线练习

### B. 编程题库

适合：算法、数据结构、编程语言练习。

题型：

- 代码题
- 测试用例
- 隐藏用例
- 时间/内存限制
- 多语言运行环境

技术重点：

- 代码编辑器
- 沙箱判题
- 容器隔离
- 资源限制
- 测试用例管理
- 安全性

### 建议

第一版优先做 **A. 知识型题库**。

原因：

1. 产品闭环更短，能更快用起来。
2. 不需要一开始就处理不可信代码执行、沙箱和语言运行时。
3. 题库导入、错题复习、间隔重复已经足够支撑一个完整项目。
4. 编程题可以作为后续独立模块接入，而不是把判题系统塞进核心 MVP。

如果编程题才是核心需求，架构需要额外增加一个独立的 Judge 服务，不能简单复用普通题目表。

## 3. 产品定位

### 3.1 不要做什么

第一版不建议做：

- 视频课程平台
- 直播课
- 内容商城
- 社区和排行榜
- 多机构、多租户
- 复杂 AI 教师
- 付费系统
- 全题型判题系统

这些功能会把项目从“个人刷题工具”拖成“在线教育平台”。

### 3.2 要做的差异化

建议围绕四个关键词：

1. **自己的题库**
   - 题目、笔记、错题、学习记录都属于自己
   - 支持完整导出，不被平台锁定

2. **导入优先**
   - CSV、Excel、Markdown、JSON
   - 后续支持 PDF、Word、截图 OCR
   - 导入后先进入“待审核区”，确认后再入库

3. **错题驱动**
   - 错题不是简单收藏，而是进入复习队列
   - 记录错误原因：概念不清、粗心、遗忘、蒙对
   - 统计“反复错”的题和知识点

4. **多端闭环**
   - 桌面端负责生产题库
   - Web 负责管理和分析
   - Android 负责每日练习和碎片时间复习
   - 后端负责同步和调度

一句话：

> 能把任何资料变成自己的题库，并在电脑和手机上持续复习。

## 4. 四个平台的职责

| 平台 | 主要职责 | 不应该承担 |
| --- | --- | --- |
| Web | 题库管理、题目编辑、导入审核、练习、统计分析、考试模拟 | 大量本地文件处理、系统级快捷键 |
| 后端 | 认证、同步、存储、搜索、复习调度、导入任务、媒体处理 | 复杂 UI、客户端本地文件访问 |
| 桌面端 | 批量导入、PDF/Word/Excel 解析、OCR、本地题库、离线练习、导出 | 复制一套完整的 Web 管理后台 |
| Android | 每日复习、随机刷题、离线练习、拍照采集、通知提醒、分享面板 | 大规模题库编辑、复杂导入 |

### 桌面端的真正价值

桌面端不应只是“把 Web 页面包一层”。

它最有价值的能力是：

- 批量导入 PDF/Word/Excel
- 截图 OCR
- 题目切分与预览
- 本地文件监听
- 离线题库
- 快速导出备份
- 全局快捷键呼出练习/搜索

如果题库主要来自现成文档，桌面端甚至应该优先于 Android 开发。

## 5. 核心领域模型

最重要的设计原则：

> 题目内容（Content）和学习状态（Learning State）必须分离。

### 5.1 内容侧

- `User`：用户
- `QuestionBank`：题库
- `Question`：题目
- `QuestionVersion`：题目版本
- `Tag` / `KnowledgePoint`：标签和知识点
- `MediaAsset`：图片、音频、附件
- `ImportBatch`：导入批次
- `SourceDocument`：原始资料来源

### 5.2 学习侧

- `PracticeSession`：一次练习
- `Attempt`：一次作答记录
- `ReviewState`：复习状态
- `Note`：个人笔记
- `ErrorReason`：错误原因
- `Device`：同步设备
- `SyncChange`：同步变更

### 5.3 为什么 Attempt 要独立

不要把“是否答对”只存在题目表里。

每次作答都应该是一条独立记录：

```text
user_id
question_id
session_id
answer
is_correct
duration_ms
confidence
error_reason
created_at
```

好处：

- 可以分析历史趋势
- 可以重建复习状态
- 可以统计反复错的题
- 可以支持多设备同步
- 不会因为修改题目而丢失历史

### 5.4 题目结构

建议使用“公共字段 + JSONB 载荷”的方式：

```text
Question
- id
- bank_id
- type
- stem
- explanation
- difficulty
- status
- payload (JSONB)
- created_at
- updated_at
```

`payload` 根据题型不同保存：

- 选项
- 正确答案
- 填空答案
- 代码模板
- 测试用例
- 评分规则
- 媒体引用

这样以后增加题型时，不需要不断给主表加大量可空字段。

### 5.5 题目版本

题目内容可能被修改，但历史作答要保留。

建议：

- `Question` 保存当前版本
- `QuestionVersion` 保存历史快照
- `Attempt` 记录作答时对应的 `question_version_id`

这样以后改题不会让历史统计失真。

## 6. 推荐技术架构

### 6.1 总体结构

```text
Web (Next.js/TypeScript) ─┐
Desktop (Tauri/Rust)      ─┼── HTTPS/JSON ── Go API ── PostgreSQL
Android (Kotlin/Compose)  ─┘                    │
                                                ├── Redis
                                                ├── S3/MinIO
                                                ├── Meilisearch（可选）
                                                └── Python Worker
```

### 6.2 技术选型

| 层 | 建议 |
| --- | --- |
| Web | Next.js + TypeScript + Tailwind CSS + TanStack Query |
| 后端 | Go + Chi/Echo + sqlc + pgx + PostgreSQL |
| 桌面 | Tauri 2 + Rust + React |
| Android | Kotlin + Jetpack Compose + Room + WorkManager |
| 后台任务 | Python + FastAPI + arq/Celery |
| 文档解析 | Python：pdfplumber、python-docx、openpyxl |
| OCR | PaddleOCR 或 Tesseract |
| 搜索 | PostgreSQL 全文搜索起步，后续 Meilisearch |
| 文件存储 | MinIO（本地）/ S3 兼容存储 |
| 部署 | Docker Compose + Caddy |
| 契约 | OpenAPI，生成 TypeScript/Kotlin 客户端 |
| CI | GitHub Actions |

### 6.3 先做模块化单体

第一版不要拆微服务。

建议一个 Go 服务内部按模块划分：

```text
internal/
  auth/
  content/
  practice/
  review/
  sync/
  analytics/
  import/
```

一个 PostgreSQL，一个 Redis，一个 Worker。

等真正的瓶颈出现，再拆服务。

## 7. 同步策略

多端同步是这个项目最容易过度设计的地方。

建议把数据分成两类：

### 7.1 内容数据

题库、题目、选项、解析、媒体。

特点：

- 写少读多
- 主要由 Web/桌面端生产
- Android 主要是下载和缓存

策略：

- 服务端维护题库版本
- 客户端增量拉取
- 媒体按需下载
- 删除使用软删除

### 7.2 学习数据

作答、笔记、复习状态、收藏。

特点：

- 写入频繁
- 离线时也会产生
- 多设备可能冲突

策略：

- `Attempt` 追加写入，天然少冲突
- 使用客户端生成的 ULID + 幂等键
- 笔记可以先使用最后写入优先
- 复习状态优先由服务端根据作答记录计算
- Android 离线时本地排队，联网后批量上传

第一版不需要 CRDT。

先把“内容下发 + 作答上传 + 简单冲突处理”做好，比直接上复杂同步框架更现实。

## 8. MVP 建议

### M0：Web + 后端闭环

- 单用户登录
- 题库 CRUD
- 题目 CRUD
- 支持单选、多选、判断三种题型
- CSV/Markdown 导入
- 练习会话
- 作答记录
- 错题本
- 简单复习队列
- JSON 导出

验收标准：

> 能导入 100 道题，完成一次 20 题练习，错题进入错题本，并能导出全部数据。

### M1：Android 练习端

- 登录
- 下载题库
- 离线练习
- 本地作答队列
- 联网同步
- 每日复习提醒
- 错题和笔记查看

### M2：桌面导入工作台

- 批量导入 Excel/Word/PDF
- OCR 截图识别
- 导入预览和人工修正
- 题目去重
- 本地题库缓存
- 导出备份

### M3：学习分析与增强

- 知识点掌握度
- 正确率、用时、错误率趋势
- 反复错题识别
- 复习计划
- AI 解析/相似题生成（可选）
- 课程/章节/学习计划

开发顺序取决于你的题库来源：

- 如果题库主要是 CSV/Excel/Markdown：先 Web + API，再 Android。
- 如果题库主要是 PDF/截图：先 Web + API，再桌面导入，再 Android。

## 9. 主要风险

### 9.1 范围膨胀

“学习平台”很容易扩展成课程、社区、直播、支付。

对策：第一版只做“题库 + 练习 + 错题 + 复习”。

### 9.2 题库导入是真正的难点

没有题库，刷题软件就是空壳。

对策：把导入做成第一优先级功能，并且必须有“待审核区”，不要让解析结果直接入库。

### 9.3 题型会不断膨胀

一开始只做 3 种题型，后续通过题型注册机制扩展。

对策：公共字段 + JSONB + 客户端渲染器注册表。

### 9.4 同步复杂度

不要在 MVP 阶段做完整 CRDT。

对策：内容下发和作答上传分开处理，复习状态服务端计算。

### 9.5 AI 依赖

AI 适合做解析、总结、相似题，但不应该成为核心答题逻辑。

对策：AI 功能异步、可关闭、可追溯，答案以人工内容和题目解析为准。

### 9.6 版权问题

如果导入的是教材、题库或付费资料，个人使用可以，但不要默认做公开分享和分发。

对策：先只做私有题库；公开分享功能后置，并加入版权和举报机制。

### 9.7 桌面端 Python 打包

OCR 和 PDF 解析通常用 Python，但把 Python 打进桌面客户端会增加复杂度。

对策：第一版可以让桌面端调用本地 Python 服务或 CLI；稳定后再考虑打包。

## 10. 扩展到“正常学习软件”

可以按下面的路径扩展，而不是一次性做完：

### 阶段一：个人刷题工具

- 题库
- 练习
- 错题
- 复习
- 统计

### 阶段二：个人学习系统

- 闪卡
- 笔记
- 学习计划
- 课程/章节
- 考试模拟

### 阶段三：多用户学习平台

- 账号体系
- 题库分享
- 班级/小组
- 讨论和评论
- 教师/学生角色
- 权限和审核

### 阶段四：内容和商业化（可选）

- 公开题库
- 课程市场
- 订阅
- 支付
- 机构版

架构上要提前留出：

- `owner_id`
- `visibility`（private/unlisted/public）
- 内容版本
- 软删除
- 审计日志
- API 版本
- 数据导出

但不要在 MVP 阶段实现这些功能。
